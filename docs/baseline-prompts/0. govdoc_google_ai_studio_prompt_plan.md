# GovDoc SecureFlow — Google AI Studio Prompt Plan (3 Passes Max)

Version: 1.0  
Purpose: Use Google AI Studio (Gemini 3.1 Flash Preview) to generate a **real frontend + real backend baseline** with **mock core/business logic only**, in a structure that later coding agents can extend without reworking the repo.

Primary inputs:
- `govdoc_source_of_truth_plan_v1_1.md`
- `govdoc_implementation_plan.md`

This plan is intentionally limited to **3 passes** to keep prompts small, explicit, and stable for Gemini Flash Preview.

---

## 1) What this prompt plan is trying to achieve

After all passes are completed, the baseline repo should have:

- a real production-style frontend
- a real backend API
- a real persistence layer
- real routing/navigation and screen structure
- real Docker / docker-compose / Makefile devops scaffolding
- real health/config handling
- real seeded demo scenarios
- **mocked core/business logic only**, isolated behind interfaces/modules so coding agents can replace them later

The baseline must **not** collapse into a generic chatbot app or a fake one-file prototype.

---

## 2) Locked stack and architecture choices

These choices are locked for the AI Studio generation so later coding agents do not need to rework the baseline.

### 2.1 Frontend stack
- **Next.js 15**
- **TypeScript**
- **App Router**
- **Tailwind CSS**
- **component library allowed**: shadcn/ui or a similar lightweight, composable UI layer

### 2.2 Backend stack
- **FastAPI**
- **Python 3.12**
- **Pydantic**
- **SQLAlchemy**
- **Alembic**
- REST API, not GraphQL

### 2.3 Persistence
- **SQLite** for baseline/MVP simplicity
- stored in a mounted volume
- no external DB service required in baseline

### 2.4 Deployment/dev workflow
- **docker-compose**
- **Makefile**
- separate `web` and `api` services
- remote host treated as plain VPS later

### 2.5 Core architecture rules
The repo must separate:
- frontend UI
- backend API
- deterministic workflow/state logic
- AI integration adapter layer
- core/business modules
- storage/extraction modules
- seeded demo scenario data
- tests

### 2.6 Mocking rule
Only the following may be mocked/faked in the baseline:
- classification result generation
- routing result generation
- summary generation
- OCR output generation
- retrieval/rerank result generation
- consultation auto-response generation

These mocks must be placed in **separate modules/files** behind interfaces/contracts.

### 2.7 Do not implement in the baseline
Do **not** implement:
- real Model Studio analysis pipeline
- real embeddings/rerank indexing
- real OCR processing
- real auth/login
- OSS/STS
- full production-grade AI quality tests
- final remote deployment script internals

The exact names can vary slightly, but the repo must clearly have these responsibilities:

```text

  prompts/

      demo/

  scripts/

    qa_local.*
    check_credentials.*
  data/
    demo_scenarios/
    fixtures/
  Makefile
  .env.example
  README.md
```

### 3.1 Mock module placement rule
The baseline must make it easy to replace mocks later.

Recommended module shape:

```text
api/app/services/ai/
  interface.py
  mock_provider.py
  future_modelstudio_provider.py

api/app/services/extraction/
  interface.py
  mock_extractor.py
  future_pdf_extractor.py
  future_ocr_provider.py

api/app/services/retrieval/
  interface.py
  mock_retriever.py
  future_embedding_retriever.py
```

Controllers/routes must depend on interfaces or service facades, **not** on mock implementations directly.

## 5) Prompting rules for Gemini 3.1 Flash Preview

These rules are here to make the prompts work better with Gemini Flash Preview.

### 5.1 Keep each pass narrow
Do not ask the model to do everything at once.

### 5.2 Lock the stack explicitly
Repeat the stack every pass.

### 5.3 Tell it what **not** to do
Gemini Flash often overreaches. Explicitly say:
- do not rewrite stack
- do not implement later passes early
- do not collapse backend into frontend
- do not use generic chat UI

### 5.4 Require a file list in output
At the end of each pass, ask for:
- files created/modified
- any assumptions made
- any gaps remaining

### 5.5 Require mock isolation
Repeat:
- mock core/business logic must be in separate modules/files
- routes/controllers should use service interfaces/facades

### 5.6 Require no giant explanatory essay
Ask the model to focus on code changes and short repo notes, not long prose.
